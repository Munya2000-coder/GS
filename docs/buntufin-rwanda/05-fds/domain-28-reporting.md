# BFR-FDS-28 — Domain 28: Reporting and Sandbox KPI (`RPT`)

**Context:** Reporting (`reporting-svc`) · **Epic:** `EPIC-RPT` — The evidence pack the sandbox is judged on
**Wave:** W6 · **Depends on:** every domain's events · **Parameterised:** `Q-11` (reporting template)

> Common rules applying to every requirement in this domain:
> **R1** Reports read from projections built from domain events, never from operational tables.
> **R2** Every report states its definition version, period and generation time, and is reproducible for the same inputs.
> **R3** Every generation and export is audited, with volume alerting (URS §21).
> **R4** A period with no activity produces a nil report, never an absent one.

### BFR-RPT-001 — Total sandbox participants `P1`

**Acceptance (URS):** Count can be generated by reporting period.

**Screens** — Reporting ▸ Participation: cumulative and new participants per period, by cohort.

**Workflow**
1. `customer.created` and `customer.verified` events build the participation projection.
2. Counts are produced per period and per cohort (`GOV-005`).

**API** — `POST /api/admin/v1/reports/participants` `{from, to, cohort?}` → 202; `GET .../reports/{id}` → 200.

**Data** — participation read model.

**Rules**
- `BR-RPT-001.1` "Participant" is a documented, versioned definition (registered, verified, or cohort member) and the definition used is printed on the report.
- `BR-RPT-001.2` Counts are point-in-time reproducible: re-running for a past period yields the same figure.
- `BR-RPT-001.3` Closed and restricted customers are counted per the definition, and their treatment is stated.
- `BR-RPT-001.4` Cohort breakdown supports the sandbox's controlled-population reporting.

**Exceptions**
- `EX-RPT-001.1` Projection lag → the report states its data-as-at time and is not generated for an incomplete period without a warning.

**Events** — consumes `customer.*`.
**Audit** — generation and export audited.

**Story `US-RPT-001`** — As a sandbox supervisor, I want participant counts per period, so that I can see the pilot's actual scale.
*Given* a reporting period, *when* I generate the participants report, *then* I get a reproducible count with its definition version.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-RPT-001-1 | POS | Count generated per period and cohort |
| TC-RPT-001-2 | POS | Re-run reproduces the same figure |
| TC-RPT-001-3 | POS | Definition version printed |
| TC-RPT-001-4 | AUD | Generation audited |

### BFR-RPT-002 — Active users `P1`

**Acceptance (URS):** Activity definition is configurable/documented.

**Screens** — Reporting ▸ Activity with the active-user definition displayed alongside the figure.

**Workflow**
1. The activity definition is configuration (default: an authenticated session plus a completed financial or Passport action in the period).
2. Counts are produced per period, with the definition version printed.

**API** — `POST /api/admin/v1/reports/active-users` → 202.

**Data** — activity read model.

**Rules**
- `BR-RPT-002.1` The definition is configuration, versioned, and shown on the report — so a change in the number can be distinguished from a change in the definition.
- `BR-RPT-002.2` Changing the definition does not retroactively alter reports already issued; a re-run under a new definition is labelled as such.
- `BR-RPT-002.3` Multiple definitions may be reported in parallel where the regulator asks for a specific basis.
- `BR-RPT-002.4` Login alone is reportable separately from transacting activity.

**Exceptions**
- `EX-RPT-002.1` Definition changed mid-period → both bases are reported, clearly labelled, rather than a blended figure.

**Events** — consumes activity events.
**Audit** — definition changes audited.

**Story `US-RPT-002`** — As a sandbox supervisor, I want a stated definition of "active user", so that the number means something specific and comparable over time.
*Given* an active-user report, *when* I read it, *then* the definition and its version are printed with the figure.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-RPT-002-1 | POS | Active users computed per the configured definition |
| TC-RPT-002-2 | POS | Definition version printed |
| TC-RPT-002-3 | NEG | Definition change does not silently alter past reports |
| TC-RPT-002-4 | POS | Parallel definitions reportable |

### BFR-RPT-010 — Export to common formats `P2`

**Acceptance (URS):** CSV/XLSX/PDF or approved reporting format can be produced.

**Screens** — Report ▸ Export with format selection; Export history.

**Workflow**
1. A generated report can be exported in the supported formats.
2. Exports are delivered through short-lived authenticated links and recorded.
3. Every export carries the report's definition version, period and generation time.

**API** — `POST /api/admin/v1/reports/{id}/export` `{format}` → 202; `GET .../exports/{eid}` → 200.

**Data** — `report_export(format, generated_at, expires_at, download_count)`

**Rules**
- `BR-RPT-010.1` Exports carry the definition version, period and generation time in the document itself, not only in the filename.
- `BR-RPT-010.2` Export links are short-lived and authenticated; there is no public URL.
- `BR-RPT-010.3` Every export is audited and large exports raise a security alert (URS §21).
- `BR-RPT-010.4` The format set is configuration, so an additional regulator-required format can be added without redesign (`Q-11`).
- `BR-RPT-010.5` Exported figures match the on-screen report exactly — one calculation, two renderings.

**Exceptions**
- `EX-RPT-010.1` Export of a report still generating → refused with the status, rather than exporting a partial file.

**Events** — `report.exported`
**Audit** — export generation and downloads audited.

**Story `US-RPT-010`** — As a compliance officer, I want reports exportable in standard formats, so that I can submit them without re-keying figures.
*Given* a generated report, *when* I export it, *then* the file carries the definition version, period and generation time, and its figures match the screen exactly.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-RPT-010-1 | POS | Export produced in each supported format |
| TC-RPT-010-2 | POS | Exported figures match the on-screen report |
| TC-RPT-010-3 | SEC | Links short-lived and authenticated |
| TC-RPT-010-4 | AUD | Export audited and volume-alerted |
| TC-RPT-010-5 | NEG | Partial export refused |
