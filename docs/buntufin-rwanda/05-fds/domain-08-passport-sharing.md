# BFR-FDS-08 — Domain 08: Financial Passport Sharing (`FPS`)

**Context:** Financial Passport (`passport-svc`) · **Epic:** `EPIC-FPS` — The customer controls who sees their financial evidence
**Wave:** W2 · **Depends on:** `FP`, `CON`, `PRT` · **Blocking question:** `Q-09`

---

### BFR-FPS-001 — Customers choose organisations to share with `P1`

**Acceptance (URS):** No organisation can browse Passport without authorised pathway.

**Screens** — Share Passport ▸ choose recipient from the configured partner directory; Review scope; Confirm.

**Workflow**
1. The customer selects a recipient from partners configured to receive Passport data.
2. Scope, duration and use limits are chosen (`FPS-002`, `FPS-003`, `FPS-004`).
3. A consent is recorded and a `passport_share` authorisation is created (`FPS-005`).
4. The recipient is notified that a share is available to them.

**API**
- `GET /api/v1/passport/share-recipients` → 200 eligible partners
- `POST /api/v1/passport/shares` → 201
- `GET /api/partner/v1/passport-shares` → 200 (shares granted **to** the calling partner only)

**Data** — `passport_share`, `consent`

**Rules**
- `BR-FPS-001.1` There is **no** partner-facing search, browse or list-by-customer endpoint. A partner can only see shares explicitly granted to it.
- `BR-FPS-001.2` Only partners whose capability includes Passport receipt appear as recipients (`PRT-002`).
- `BR-FPS-001.3` Every share requires a consent whose purpose matches the sharing purpose (`CON-003`).
- `BR-FPS-001.4` A suspended partner cannot be selected and cannot read existing shares (`PRT-003`).

**Exceptions**
- `EX-FPS-001.1` Partner attempts to access a Passport without a share → `404`, logged as a security event.
- `EX-FPS-001.2` Recipient not enabled for Passport receipt → `VALIDATION_FAILED`.

**Events** — `passport.shared`
**Audit** — share creation with recipient, scope, expiry and consent reference.

**Story `US-FPS-001`** — As a customer, I want to choose exactly which organisation sees my Passport, so that no institution can look me up without my permission.
*Given* no share exists, *when* a partner attempts to read my Passport, *then* it is not found and the attempt is recorded.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-FPS-001-1 | POS | Share created for a chosen recipient |
| TC-FPS-001-2 | SEC | No browse or search endpoint exists for partners |
| TC-FPS-001-3 | SEC | Access without a share returns 404 and raises a security event |
| TC-FPS-001-4 | NEG | Partner without the capability cannot be selected |
| TC-FPS-001-5 | INT | Suspended partner cannot read existing shares |

### BFR-FPS-002 — Customers choose data categories shared `P1`

**Acceptance (URS):** User can include/exclude supported Passport sections.

**Screens** — Share ▸ section toggles (Identity, Income, Cashflow, Savings, Business, Circle behaviour) with a live preview of what the recipient will see.

**Workflow**
1. The customer toggles sections on or off.
2. A preview shows the recipient's exact view.
3. The selected scope is stored on the share and enforced on every read.

**API** — `POST /api/v1/passport/shares` with `scopes[]`; `GET /api/v1/passport/shares/{id}/preview` → 200.

**Data** — `share_scope(section, included)`

**Rules**
- `BR-FPS-002.1` Scope is enforced **server-side** at read time; excluded sections are never serialised, not merely hidden.
- `BR-FPS-002.2` The preview is generated by the same code path as the recipient view, so what the customer sees is what the recipient gets.
- `BR-FPS-002.3` A recipient requesting an excluded section receives a scope denial, recorded in the access log.
- `BR-FPS-002.4` Sections a partner requires for its stated purpose may be marked recommended, never pre-selected in a way that obscures the choice.

**Exceptions**
- `EX-FPS-002.1` Empty scope selection → `VALIDATION_FAILED`; an empty share is not created.
- `EX-FPS-002.2` Request for an out-of-scope section → `PERMISSION_DENIED`, logged with result `DENIED_SCOPE`.

**Events** — `passport.shared` carrying the scope list.
**Audit** — scope recorded and immutable for the life of the share.

**Story `US-FPS-002`** — As a customer, I want to share only the parts of my Passport that are relevant, so that a lender assessing a business loan does not see everything about my personal life.
*Given* a share excluding savings, *when* the recipient requests savings data, *then* it is refused and the attempt is logged.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-FPS-002-1 | POS | Only included sections are returned |
| TC-FPS-002-2 | SEC | Excluded sections absent from the payload entirely |
| TC-FPS-002-3 | POS | Preview matches the recipient view exactly |
| TC-FPS-002-4 | NEG | Empty scope rejected |
| TC-FPS-002-5 | AUD | Out-of-scope request logged as DENIED_SCOPE |

### BFR-FPS-003 — Time-limited sharing `P1`

**Acceptance (URS):** Access automatically expires at specified timestamp.

**Screens** — Share ▸ duration selector with the exact expiry shown; Active shares list with countdown.

**Workflow**
1. The customer chooses a duration within the configured maximum.
2. `expires_at` is stored on the share.
3. Every recipient read re-evaluates expiry at request time; after expiry the share is unusable.

**API** — `POST /api/v1/passport/shares` with `expires_at`; recipient reads return `410`/`403` after expiry.

**Data** — `passport_share.expires_at`, `.status`

**Rules**
- `BR-FPS-003.1` Expiry is enforced at read time, not by a sweep job alone.
- `BR-FPS-003.2` Maximum share duration is configuration (`GOV-001`).
- `BR-FPS-003.3` Expiry cannot be extended; a longer share is a new authorisation with new consent.
- `BR-FPS-003.4` Data already lawfully received by the recipient before expiry is outside platform control; the customer is told this plainly when creating a share.

**Exceptions**
- `EX-FPS-003.1` Read after expiry → denied, logged as `DENIED_EXPIRED`, and the recipient is told it has expired rather than that nothing exists.

**Events** — `passport.share.expired`
**Audit** — expiry-time denials recorded.

**Story `US-FPS-003`** — As a customer, I want my share to expire automatically, so that a one-off application does not give permanent access.
*Given* an expired share, *when* the recipient attempts to read it, *then* access is refused and recorded.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-FPS-003-1 | POS | Share readable before expiry |
| TC-FPS-003-2 | NEG | Read after expiry refused at request time |
| TC-FPS-003-3 | NEG | Duration beyond configured maximum refused |
| TC-FPS-003-4 | NEG | Expiry cannot be extended in place |
| TC-FPS-003-5 | AUD | Expired access attempt logged |

### BFR-FPS-004 — One-time sharing `P1`

**Acceptance (URS):** Recipient cannot reuse expired one-time authorisation.

**Screens** — Share ▸ "single view only" option, explained plainly.

**Workflow**
1. The customer selects single-use; `max_access_count = 1`.
2. The first successful recipient read increments `access_count` and exhausts the share.
3. Further reads are refused.

**API** — `POST /api/v1/passport/shares` with `max_access_count: 1`.

**Data** — `passport_share.max_access_count`, `.access_count`, `.status = EXHAUSTED`

**Rules**
- `BR-FPS-004.1` The counter is incremented atomically with the read, so concurrent requests cannot both succeed.
- `BR-FPS-004.2` A failed or denied read does not consume the single use.
- `BR-FPS-004.3` Exhaustion is permanent; reuse requires a new share.
- `BR-FPS-004.4` The recipient is told before reading that the share is single-use.

**Exceptions**
- `EX-FPS-004.1` Second read → denied, logged as `DENIED_EXHAUSTED`.
- `EX-FPS-004.2` Read that fails mid-response → use not consumed; the failure is logged.

**Events** — `passport.accessed`, `passport.share.exhausted`
**Audit** — every access attempt with its result.

**Story `US-FPS-004`** — As a customer, I want to share my Passport once only, so that a single application does not become ongoing access.
*Given* a single-use share already read, *when* the recipient tries again, *then* it is refused and recorded.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-FPS-004-1 | POS | First read succeeds |
| TC-FPS-004-2 | NEG | Second read refused |
| TC-FPS-004-3 | CON | Concurrent reads: exactly one succeeds |
| TC-FPS-004-4 | NEG | Denied read does not consume the single use |
| TC-FPS-004-5 | AUD | All attempts logged with result |

### BFR-FPS-005 — Sharing generates unique authorisation `P1`

**Acceptance (URS):** Each share has unique ID, scope, recipient and expiry.

**Screens** — Share created ▸ reference shown to the customer; Active shares list.

**Workflow**
1. Each share is created with a unique id and a high-entropy token whose hash is stored.
2. The authorisation binds recipient, scope, expiry and use limit.
3. The recipient authenticates as itself **and** presents the share reference — the token alone is never sufficient.

**API** — `POST /api/v1/passport/shares` → 201 `{share_id, reference, expires_at}`.

**Data** — `passport_share.share_token_hash`

**Rules**
- `BR-FPS-005.1` Share tokens are stored hashed, never in plaintext.
- `BR-FPS-005.2` Possession of a share reference is not sufficient authorisation — the recipient must also be the authenticated bound partner.
- `BR-FPS-005.3` Share ids are unguessable UUIDs; enumeration is not possible.
- `BR-FPS-005.4` One share serves one recipient; sharing with two organisations creates two authorisations with independent lifecycles.

**Exceptions**
- `EX-FPS-005.1` Correct token presented by the wrong partner → `404` and a security event (a strong signal of leakage).

**Events** — `passport.shared`
**Audit** — creation and every use.

**Story `US-FPS-005`** — As a compliance officer, I want each share to be a unique, scoped, bound authorisation, so that access is never transferable between organisations.
*Given* a share issued to partner A, *when* partner B presents its reference, *then* access is refused and a security event is raised.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-FPS-005-1 | POS | Unique authorisation created with all four attributes |
| TC-FPS-005-2 | SEC | Token stored hashed only |
| TC-FPS-005-3 | SEC | Wrong partner with a valid token refused, security event raised |
| TC-FPS-005-4 | SEC | Share ids not enumerable |
| TC-FPS-005-5 | POS | Two recipients receive independent shares |

### BFR-FPS-006 — Customers see who accessed shared data `P1`

**Acceptance (URS):** Access event appears in customer data-access history.

**Screens** — Privacy ▸ Who accessed my Passport: organisation, sections returned, timestamp, result.

**Workflow**
1. Every recipient read writes a `share_access_log` row before the response is released.
2. The customer's data-access history reads from that log.
3. Denied attempts are shown too, so the customer sees attempted as well as successful access.

**API** — `GET /api/v1/privacy/passport-access?from=&to=` → 200.

**Data** — `share_access_log` (append-only)

**Rules**
- `BR-FPS-006.1` If the access log write fails, the data is not released.
- `BR-FPS-006.2` Both granted and denied accesses are logged and shown.
- `BR-FPS-006.3` The log records which sections were actually returned, not merely which were in scope.
- `BR-FPS-006.4` Abnormal access volume by a partner raises a security alert (URS §21 "mass Passport access").

**Exceptions**
- `EX-FPS-006.1` Log write failure → `INTERNAL_ERROR`, nothing disclosed.

**Events** — `passport.accessed`
**Audit** — the log is the audit; mirrored to `audit_event`.

**Story `US-FPS-006`** — As a customer, I want to see every time an organisation looked at my Passport, so that I can confirm my permissions were respected.
*Given* a partner read my Passport, *when* I check my access history, *then* I see who, what sections, when and with what result.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-FPS-006-1 | POS | Successful access appears in history |
| TC-FPS-006-2 | POS | Denied attempts also appear |
| TC-FPS-006-3 | ERR | Log write failure prevents disclosure |
| TC-FPS-006-4 | SEC | Log append-only |
| TC-FPS-006-5 | INT | Mass access raises a security alert |

### BFR-FPS-007 — Customers revoke active shares `P1`

**Acceptance (URS):** Future recipient access is prevented after revocation.

**Screens** — Active shares ▸ Revoke, with a clear statement that data already received cannot be recalled.

**Workflow**
1. Customer revokes a share.
2. `revoked_at` is set and status becomes `REVOKED`.
3. Subsequent recipient reads are refused at request time; the recipient may be notified per configuration.

**API** — `POST /api/v1/passport/shares/{id}/revoke` → 200.

**Data** — `passport_share.revoked_at`, `.status`

**Rules**
- `BR-FPS-007.1` Revocation is evaluated at read time, so it is effective immediately.
- `BR-FPS-007.2` Revoking the underlying consent revokes dependent shares automatically (`CON-005`).
- `BR-FPS-007.3` The customer is told honestly that already-received data cannot be recalled.
- `BR-FPS-007.4` Where the recipient has an application in progress, revocation is permitted and the consequence is explained (the application may be declined for want of information) — the customer's control is not overridden by commercial convenience.

**Exceptions**
- `EX-FPS-007.1` Read after revocation → denied, logged as `DENIED_REVOKED`.
- `EX-FPS-007.2` Revoking an already-revoked share → idempotent 200.

**Events** — `passport.revoked`
**Audit** — revocation actor, time and any cascade.

**Story `US-FPS-007`** — As a customer, I want to withdraw a share at any time, so that I stay in control even after I have granted access.
*Given* an active share, *when* I revoke it, *then* the recipient's next read is refused.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-FPS-007-1 | POS | Revocation prevents the next read |
| TC-FPS-007-2 | POS | Consent revocation cascades to shares |
| TC-FPS-007-3 | IDM | Repeat revocation idempotent |
| TC-FPS-007-4 | AUD | Denied read logged as DENIED_REVOKED |
| TC-FPS-007-5 | POS | Revocation permitted mid-application, with the consequence explained |

### BFR-FPS-008 — Shared data carries calculation timestamp `P1`

**Acceptance (URS):** Recipient sees currency and freshness date of metrics.

**Screens** — Recipient view: every metric shows "calculated on" and "data covers"; summary freshness banner.

**Workflow**
1. Every metric returned to a recipient includes `calculated_at`, its calculation period and its algorithm version.
2. A share-level freshness summary states the oldest and newest calculation in the payload.

**API** — recipient responses include `calculated_at`, `calculation_period`, `algorithm_version`, `data_as_of`.

**Data** — `passport_metric.calculated_at`, period columns

**Rules**
- `BR-FPS-008.1` Timestamps are mandatory in every recipient payload and export — a metric without one is not returned.
- `BR-FPS-008.2` The freshness shown is the calculation time and the underlying data coverage, which are distinct and both shown.
- `BR-FPS-008.3` A figure shared under one algorithm version continues to display that version even after a later recalculation (`CAT-009`, `FP-009`).

**Exceptions**
- `EX-FPS-008.1` Metric missing a timestamp → excluded from the payload and alerted as a defect.

**Events** — none
**Audit** — none additional.

**Story `US-FPS-008`** — As a lender, I want to know when each figure was calculated and what period it covers, so that I do not treat old information as current.
*Given* a shared Passport, *when* I view a metric, *then* I see its calculation date, its data coverage period and its methodology version.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-FPS-008-1 | POS | Every recipient metric carries timestamp and period |
| TC-FPS-008-2 | NEG | Metric without a timestamp is not returned |
| TC-FPS-008-3 | POS | Calculation time and data coverage shown separately |
| TC-FPS-008-4 | POS | Shared figure retains its original version reference |

### BFR-FPS-009 — Passport export `P2`

**Acceptance (URS):** User can generate controlled PDF or digital report.

**Screens** — Passport ▸ Export ▸ choose sections and format; Export ready.

**Workflow**
1. The customer selects sections and format.
2. An export job renders the report with disclaimer (`FP-010`), sources, explanations and timestamps.
3. The export is delivered through a short-lived authenticated link and its generation is logged.

**API** — `POST /api/v1/passport/exports` → 202 job; `GET /api/v1/passport/exports/{id}` → 200 status and link.

**Data** — `passport_export(sections, format, generated_at, expires_at, download_count)`

**Rules**
- `BR-FPS-009.1` Exports carry the disclaimer on every page (`FP-010`).
- `BR-FPS-009.2` Export links are short-lived, single-customer and authenticated; there is no public URL.
- `BR-FPS-009.3` Every export includes the calculation timestamps and the source list — a bare figure sheet is not permitted.
- `BR-FPS-009.4` Export generation is logged in the customer's data-access history (`FPS-006`), because a file leaves the platform's control.
- `BR-FPS-009.5` Large or unusual export volume raises a security alert (URS §21).

**Exceptions**
- `EX-FPS-009.1` Export requested with no eligible metrics → refused with an explanation rather than an empty document.

**Events** — `passport.exported`
**Audit** — export generation, sections, format and downloads.

**Story `US-FPS-009`** — As a customer, I want a document version of my Passport, so that I can present it where a digital share is not possible.
*Given* my Passport, *when* I export it, *then* I receive a document containing the metrics, sources, explanations, timestamps and the disclaimer.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-FPS-009-1 | POS | Export contains metrics, sources, explanations, timestamps |
| TC-FPS-009-2 | POS | Disclaimer on every page |
| TC-FPS-009-3 | SEC | Download link short-lived and authenticated |
| TC-FPS-009-4 | AUD | Export appears in data-access history |
| TC-FPS-009-5 | INT | Unusual export volume alerts |

### BFR-FPS-010 — Expired data is not represented as current `P1`

**Acceptance (URS):** Stale/expired indicators are visually labelled.

**Screens** — Stale metrics carry an icon plus text label ("Based on data last updated 3 May") in customer, recipient and export views.

**Workflow**
1. A metric becomes `STALE` when its underlying data is older than the configured freshness window, or its source connection has failed or been disconnected.
2. Stale metrics render with a visible label everywhere they appear.
3. Severely stale metrics are withheld entirely rather than shown.

**API** — metrics carry `status ∈ {CURRENT, SUPERSEDED, STALE, INSUFFICIENT_DATA}` and `data_as_of`.

**Data** — `passport_metric.status`, freshness thresholds in configuration

**Rules**
- `BR-FPS-010.1` Staleness is labelled with an icon **and** text, never colour alone (URS §20).
- `BR-FPS-010.2` Freshness windows and the withhold threshold are configuration.
- `BR-FPS-010.3` A disconnected source immediately makes its dependent metrics stale (`OF-010`).
- `BR-FPS-010.4` Recipients see the same staleness labelling as the customer — no clean-looking recipient view over stale data.

**Exceptions**
- `EX-FPS-010.1` Metric beyond the withhold threshold → not returned; the recipient is told it is unavailable due to age, not given an old number.

**Events** — `passport.updated`
**Audit** — none additional.

**Story `US-FPS-010`** — As a lender, I want stale figures clearly marked, so that I never mistake old data for a current position.
*Given* a metric based on data three months old, *when* I view the shared Passport, *then* it is visibly labelled as based on older data.

**Tests**
| TC | Cat | Case |
|---|---|---|
| TC-FPS-010-1 | POS | Stale metric labelled in customer, recipient and export views |
| TC-FPS-010-2 | POS | Label uses icon and text, not colour alone |
| TC-FPS-010-3 | POS | Disconnected source makes dependent metrics stale |
| TC-FPS-010-4 | NEG | Beyond-threshold metric withheld, not shown as current |
| TC-FPS-010-5 | POS | Freshness window configurable |
